# Creature transformation foundation

This catalog is **app-owned data**, not the 5etools-utils `monsterTemplate` format. A monster template in `data/bestiary/template.json` participates in `_copy._templates` when an existing stat block is loaded; it does not apply a recipe to an arbitrary selected NPC. `templateReference` is a checked source pointer only. Never pass it to `_copy`, and do not change either upstream schema or the existing template file to add new transformations.

## Preview contract

`js/creature-transformations.js` exports:

- `pLoadCreatureTransformationCandidates({dataUtil?, onWarning?})`: loads the validated-on-build catalog and site, installed prerelease, and installed homebrew races from `DataUtil.race`. The normal race loader merges site and externally adopted subraces with `Renderer.race.mergeSubraces`; inline `_versions` expand with `DataUtil.generic.getVersions`. A failed source load still rejects. Runtime candidate-validation failures exclude the entire invalid recipe (including its options), log its identity and reason, and notify `onWarning` with `{kind, index, name, source, reason}`. The shared editor shows these exclusions while healthy recipes remain usable; an invalid species version excludes its owning species, not just some of its effects. Unknown exceptions, ambiguous catalog identities, missing copy parents, and saved-operation failures remain hard errors. This does not relax legacy `monsterTemplate` or generic `_copy`/`_mod` resolution.
- `getCreatureTransformationCandidates({catalog, races, getVersions})`: pure construction from already-resolved races. IDs are case-normalized `catalog:name|source` or `race:name|source`. Versions use the extra `~v:baseName|baseSource:1-based-index` discriminator, including when a version has exactly the base race's name. Distinct sources (such as `Shadow Dragon|MM` and `Shadow Dragon|BEG`) remain distinct candidates. Repeated identical race definitions from site, prerelease, or installed homebrew collapse to one choice. Different definitions with the same race name and source receive stable `~d:<hash>` IDs and visible variant numbers, so one homebrew collision does not disable the whole picker; duplicates in the authored catalog still fail.
- `resolveCreatureTransformation({candidates, id, selections = {}})`: returns a **new**, non-executable `{id, kind, identity, provenance, eligibility, prerequisites, selectedOptions, changes, manualReview}`. `selections` is a map of option-group ID to an array of option IDs. Required, single-choice, unknown, duplicate, and `appliesTo`-gated selections are checked. `eligibility` is an **array of conjunctive constraints**: the base recipe plus each chosen option's constraint. It is not silently enforced without a selected creature.

Pure candidate construction remains strict unless explicitly given `onInvalidCandidate`; build/schema validation therefore still rejects invalid authored data. Runtime warning callbacks are additive: candidate arrays and healthy IDs, ordering, options, and mechanics are unchanged. Apply revalidates the live catalog and refreshes the exclusions rather than hiding warnings behind a success message.

`identity` always has `{name, source}`. A source must be installed or otherwise resolvable by the eventual browser for linked entities; no bare display-name fallback is permitted. The `provenance` of published recipes has edition and a verified page. For `BEG`, `published-example` page 25 belongs to the enclosing Adult Black Shadow Dragon **example**, not a page printed on the embedded template. The screenshots supplied for `SCRE` have no verified page or edition; `SCRE` is a provisional, user-attributed Spectre Creations source key pending verification. The screenshot markings do not independently establish that publisher. Never present an invented page as fact.

For species, conversion now emits fixed ability-score adjustments, a single known size and type, numeric senses and speeds, walking-relative speeds, fixed damage/condition defenses and languages, renderable source-qualified trait entries, and concrete spells available from character level 1. Finite supported choices become **required** `optionGroups` with one selected option; do not silently choose a size, ancestry bonus, resistance, language, or spell tradition. Resolve the selections before previewing. Source races with `_copy` are resolved by the existing `DataUtil.race.pMergeCopy` before inline versions expand; missing parents fail the load instead of producing an incomplete picker. Unbounded/conditional grants, unsupported entry structures, unsourced mixed-parent/subrace traits, lineage and feat choices, and later-level spells are `manualReview` items, not implied mechanics. Multiple unnamed spell blocks cannot safely be distinguished as alternatives or cumulative grants and are left for DM review. Every copied species trait is *displayed rules text*: it does **not** silently change saves, attack rolls, skills, proficiencies, or AC. A species which would make no executable change to the chosen monster is skipped with a specific reason, not recorded as a successful no-op; already-saved legacy no-op operations still replay.

In Bestiary and Encounter Workspace, the shared Templates tab lists source-qualified recipes alongside the existing source, search, and selection controls. Hover or keyboard focus on a recipe, option name, or option-group legend opens the site's native rules hover. Group legends preview the available choices without selecting one; tap or activate a legend to open the same hover on touch or keyboard. Option-name hovers separate actual automatic effects (including nested entry content) from DM-only review, with provenance and eligibility. On touch, tapping an option name shows its hover and still selects the option; its adjacent info button shows the same rules without selecting it. The selected Species recipe has its own info button beside its heading. Required choices remain unselected until chosen; optional single-choice groups include a "None" radio. Selecting a recipe and all required choices immediately shows a **read-only** before/after statblock and compact mechanical delta beside the choices. The delta spells out abilities, creature type, size, defenses, senses, languages, and walking-relative speed with before/after values; armor restrictions and retained alternate speeds remain explicit, never shown as unrestricted flight. Recipes without choices use the full available width. The per-target detailed diff remains available for exact field inspection. Changing a choice or filter refreshes or invalidates that preview and clears old conflict-winner decisions; Species retains its source-qualified dropdown. Ineligible bulk targets and their reasons are listed separately.

The automatic preview can provisionally satisfy narrative prerequisites and DM approval **only for display**. It never creates an operation or writes an override. Apply is beside the choices; it first asks for the actual prerequisites and DM approval where required, then reloads the catalog and checks the live selection, options, target histories, conflict winners, and storage limits before constructing an operation. If validation changes which bulk targets can be saved (for example, a 100-operation cap), it shows the revised skips and requires another Apply; failed or stale saves are not reported as success. Conflict winners are explicit per target. The collapsed DM-review list is informational: AC, HP, attacks, CR, and character-level adjudication are not performed automatically.

### Typed steps

The schema at `schema/site/creature-transformation.json` is strict, with no arbitrary path, JavaScript, regex, or `_copy._mod` execution. A later engine must first check all eligibility and prerequisites against the chosen monster and adjudicate `manualReview`. The permitted `changes` are:

| Step | Bounded meaning |
| --- | --- |
| `setType {value}` | Replace only the creature's type; review tags separately. |
| `setSize {value}` | Replace only the creature's size with one selected/known size; keep HP, AC, attacks, and Hit Dice for review. |
| `setAbility/minimumAbility/maximumAbility {ability,value}` | Exact score, lower bound, or upper bound; preserve other abilities. |
| `adjustAbility {ability,amount,floor:1}` / `scaleAbility {ability,factor:0.5,round:"down",floor:1}` | Apply a fixed delta or halve a score with a minimum of 1. Recheck dependent calculations. |
| `grantResistance/grantImmunity/grantVulnerability/grantConditionImmunity {value}` | Add the fixed, unconditional typed value without replacing existing defenses. |
| `grantConditionalDefense {kind,value,when}` | Add one resistance or immunity only under `nonmagical`, `nonmagicalUnsilvered`, or `dimLightOrDarkness`; never promote it to unconditional defense. |
| `grantSense {sense,range}` / `grantSpeed {mode,feet}` | Retain the better existing numeric sense or movement mode, respectively; do not replace unrelated modes. Conditional ranges and lost modes require manual review. |
| `grantRelativeSpeed {mode,relativeTo:"walk",condition?}` | Grant a climb, swim, fly, or burrow speed equal to the **effective** walking speed after preceding changes, retaining a better existing speed. The sole supported condition is `noMediumOrHeavyArmor`: Fairy-style flight is printed as a conditional monster speed, never unrestricted; an existing unconditional speed is retained with conditional flight under `speed.alternate`. A missing/ambiguous walking speed fails preview. Structured `true` species speeds and narrow top-level grant text are eligible; Dhampir's unconditional Spider Climb grants climb while its separate optional Ancestral Legacy speed retention remains for DM review and its level-3 ceiling movement remains trait text only. Nested picks, temporary or level-gated powers, and unknown restrictions require DM review. |
| `grantLanguage {value}` | Add a fixed spoken language; understanding without speech requires manual review. |
| `grantSpell {spell,source,usage,ability?,uses?}` | Add one source-qualified spell as a separate spellcasting entry. `will`/`daily`/`rest` retain concrete usage; known/prepared leveled spells display a spell link but confer no invented slots. The DM resolves spell DCs and attack modifiers. `uses` is required only for daily/rest grants. |
| `addEntry {section,entry}` | Add a source-qualified statblock entry. The bounded entry subset includes nested entries, lists/items, insets, and tables; unsupported or oversized source content is flagged rather than flattened or partially copied. |
| `removeEntry/replaceEntry {section,match,...}` | Match exactly one named entry plus source, or exactly one well-defined role plus source; zero or multiple matches **fail**. `replaceEntry.onMissing:"skip"` is only for explicitly optional source abilities. |
| `replaceDamageType {section,match,from,to,onMissing}` | Match exactly one action then replace only the listed damage types, retaining its dice, DC, and other text. `onMissing:"skip"` applies to absent optional damage, not an ambiguous or missing action. |

Entry sections are `trait`, `action`, `bonus`, `reaction`, and `legendary`. Match source `$chassis` resolves to the chosen creature's own source; other sources are explicit. The engine makes this identity check fail closed. `entry.source` records provenance; source-ambiguous mixed-parent/homebrew subrace text is not misattributed to the subrace. No legacy step modifies unrelated AC, HP, attacks, CR, or character-level state. All five are explicitly returned for DM review, as are template-specific unresolved abilities. `manualReview` is a blocking to-do list for a DM, not a simulated automation. The internal numeric-only v2 exception below does not change this default contract.

For example, `resolveCreatureTransformation({candidates, id: "catalog:half-dragon|mm", selections: {ancestry: ["red"], size: ["huge"]}})` returns resistance to fire and checked source guidance for the Huge breath. It does **not** fabricate a new breath attack, assume the source's optional CR floor is a mandatory prerequisite, or change the NPC's current HP.

The MM Shadow Dragon breath step covers every supported damage type, including gem-dragon breath damage; its bite step remains limited to the five listed types. Lethal Shadow Breath's Humanoid-to-shadow consequence requires DM review rather than spawning a creature automatically. Resolved DMG Skeleton race candidates grant bludgeoning vulnerability; finite typed vulnerability choices are explicit required options and unrepresentable choices remain for DM review. Fey Beast requires at least one feature pick, and still permits multiple picks. The screenshot recipe's page and edition remain unverified.

Existing approved Encounter operations are replayed from their saved, typed `resolved` recipe, not recomputed against today's race data. Replay permits historical no-op species operations but new previews reject them. The editor's provisional read-only display does not satisfy the engine's consent requirement for saving: real approval and prerequisite acknowledgments are required at Apply and checked again on replay. Stale previews, per-field conflict winners, and the operation-size ceiling still apply. Recipe and option hovers describe `setSize`, `grantSpell`, `grantRelativeSpeed`, and nested trait entries without treating prose as automated roll modifiers.

### Staged version-2 compilation (internal only)

The Dracolich (MM, p. 83) recipe has an optional, strictly validated `automation: {version: 2, profile: "dracolich", rollout: "staged", changes}` descriptor. **The editor does not opt in:** normal resolution, Apply, existing recipes and Species behavior remain unchanged. This first unit proves compilation and saved replay, not complete Dracolich or catalog automation. It adds no UI, estimated CR, forms or combat adjudication.

Internal callers explicitly request `resolveCreatureTransformation({candidates, id: "catalog:dracolich|mm", automationVersion: 2})`. That pending result cannot be normalized or executed directly. `previewCreatureTransformationTargets` accepts `automationInputs`, keyed by selected target ID, and compiles inside the target loop against each target's actual operation history. Each input must explicitly confirm `age: "adult" | "ancient"`, `trueDragon: true`, `shadowDragon: false`, `physiology: "amphibious-only"` and `lairActions: "retain"`. Age and dragon identity are supplied adjudications, not guessed from a creature's name. Non-dragons, explicitly ineligible ages/natures and Living Shadow subjects are rejected. Missing confirmations, additional living-physiology decisions and requested lair changes produce a named unresolved-input skip, never a successful partial application.

The pure `compileCreatureTransformation({resolved, current, chassisSource?, inputs})` retains the sourced legacy type/defense changes, adds source-qualified Magic Resistance and the complete no-air/food/drink/sleep rule, and emits an exact source-qualified removal only when the current target has one unambiguous Amphibious trait. `chassisSource` supplies the original creature's source for unqualified traits, matching executor identity semantics. Multiple Amphibious candidates fail closed. Unrelated stats, attacks, traits, lair references and existing defenses are retained. The generic chassis-review items remain; this stage does not claim their later automation.

The concrete result has `version: 2`, bounded typed changes and frozen confirmation receipts in the four `selectedOptions` groups `automation-age`, `automation-nature`, `automation-physiology` and `automation-lair`. It contains no executable descriptor, profile pointer or conditional interpreter. The adapter and executor recognize only this closed staged profile; all existing per-step validation still applies. Concrete snapshots cannot be reused as batch recipes: new workflow previews must start from the pending profile and compile independently. `createCreatureTransformationChanges` recompiles against the checked histories and inputs before saving. Internal callers may pass fresh `resolved` and `automationInputs` there to fence changed catalog data or decisions; the editor's existing live-catalog validation remains unchanged.

Preview, real prerequisite/DM consent, conflicts, storage preflight, integrity and stale-history guards still apply. The staged result explicitly requires DM approval for its supplied eligibility/physiology adjudications; this does not change legacy recipe consent. Operations save only the concrete result and replay without catalog loading or recompilation, even after the live descriptor changes or disappears. Removing an operation restores the underlying history. Unversioned legacy operations—including incomplete Dracolich, breathless Half-Dragon and historical Species operations—retain their original contents and behavior. Other Template families, complete physiology/lair choices, guided UI, additional dependent calculations and estimated CR require separately approved later units.

### M2a numeric-only compilation (internal only)

`Zombie|DMG` (p. 282) is the **sole additional staged representative**, with `automation: {version: 2, profile: "zombie-numerics", rollout: "staged", hitPoints: "constitution"}`. This exercises the real catalog-to-target numerical boundary, not a completed Zombie family: Undead Fortitude, lost capabilities and language restrictions remain explicit unresolved review items. The editor does not opt in, and Dracolich M1 snapshots, all default recipes and Species retain their old identities, contents and behavior. Callers must explicitly resolve `catalog:zombie|dmg` with `automationVersion: 2`; its target inputs are empty, and its PB is retained. The source's +1 STR, +2 CON, -6 INT, -4 WIS and -4 CHA changes are applied to each actual target history, not copied from the MM Zombie.

The pure `compileCreatureTransformationStats({current, abilities?, hp?, proficiencyBonus?, nextProficiencyBonus?, bindings?})` shares the existing Parser ability and skill mappings, but never invokes CR scaling. Its independent rule oracles are MM pp. 7-9 (HP, saves and skills) and DMG p. 279 (passive Perception). It emits concrete `setAbility` plus only these five new, strict setters: `setHitPoints {value:{average,formula}}`, `setSaveBonus {ability,value}`, `setSkillBonus {skill,value}`, `setPassivePerception {value}`, and `setProficiencyBonus {value}`. Bonus setter values are integers; the executor formats saves/skills with their sign. `numericChange` in the app schema describes this concrete output only: these setters are forbidden in default recipe/option changes and unversioned operations.

HP policies are explicit and closed:

- `{mode:"constitution"}` (default) accepts one bounded `Nd4/6/8/10/12/20` term with an optional signed integer bonus. It separates `count * old CON modifier` from the existing non-CON bonus, retains the latter, and adds `count * new CON modifier` exactly once. Optional `hitDice:{number,faces}` changes count/faces; if count changes with a nonzero residual, `residual:{perHitDie,fixed}` must exactly explain the existing non-CON bonus. Optional `bonusPerHitDie` and `bonusFixed` are **independent new grants**, not another application of a source's CON change. Average HP is the rounded-down formula mean, with a total minimum of 1.
- `{mode:"retain"}` deliberately preserves the authored chassis HP, including special HP. It cannot be combined with numerical adjustments.
- `{mode:"override",value:{average,formula}}` uses an explicit concrete authored override without subsequently adding CON again. An override may deliberately specify a non-mean average. Without this explicit policy, a current average/formula disagreement blocks reconciliation instead of guessing its meaning.

For example, the MM Knight's CON 14 and `52 (8d8 + 16)` become CON 16 and `60 (8d8 + 24)`; its CON save changes from +4 to +5. An unchanged die count preserves fixed or per-die extras without guessing their decomposition. Formula parsing has no expression evaluation. Counts are 1-10,000, total formula bonuses are within +/-1,000,000, and HP averages are 1-1,000,000. Unsupported/mixed formulas, special HP without a retain/override policy, malformed scores, or unexplained residual bindings produce `CREATURE_TRANSFORMATION_INPUT_REQUIRED`, not an invented number.

Listed saves/skills retain their total's authored residual and proficiency/expertise contributions. With unchanged PB, only the relevant ability-modifier delta is needed, so no proficiency is guessed from a large bonus. A PB change requires `current.profBonus`, a plain numeric `pbNote`, or an explicit agreeing `proficiencyBonus`, plus an explicit multiplier (0, 1 or 2) for **every** listed save/skill under `bindings.save` / `bindings.skill`. Existing numeric PB sources must agree. The calculation is `old total + ability delta + multiplier * PB delta`; fixed residuals are not discarded. No CR-to-PB estimate is made. Passive Perception changes by the Perception-bonus delta (or WIS delta without that skill), preserving any authored passive-only residual; a missing passive is initialized to 10 plus the effective Perception bonus. Conditional/alternative skill maps, nonnumeric bonuses/passive values, unsupported multipliers and missing PB bindings block the entire target with a precise input reason.

`setProficiencyBonus` atomically sets **both** the engine's numeric `profBonus` and the renderer/Compare's canonical string `pbNote` (for example, `3` and `"+3"`), without changing CR. Both fields receive independent concrete write/conflict records within the dependent numeric conflict group, including when only the old note changes. An explicit request for the already-current engine PB still emits the setter if its display note needs synchronization. A present note must be a plain positive integer string, optionally prefixed with `+`, in the supported 1-30 range; conditional, formula, prose, empty or non-string notes are not silently replaced. A disagreement between existing `profBonus` and a numeric `pbNote` also requires explicit source resolution before any PB write. These checks run in compilation **and** at the concrete setter/replay boundary. A profile that does not request a PB change, including staged Zombie without M3 inputs, retains its authored PB note untouched. Real-renderer regressions cover CR fallback, an existing numeric note, unchanged engine PB, frozen replay, removal and paired/note-only conflict decisions.

Compilation freezes each target's actual output into concrete setters and the `automation-numerics:["zombie-dmg-m2a"]` receipt, never an executable formula/profile descriptor. Replay does not load today's catalog or recompute those numbers. Removing the operation restores its underlying history; old saved Zombie operations are not silently upgraded. Dependent numeric fields form one conflict unit: all incoming numerical conflict winners apply the compiled group, all existing winners retain the current numeric group, unresolved conflicts withhold the group, and mixed winners fail explicitly. Consent, live-history/input fences, operation integrity and target-specific storage preflight remain required.

This unit does **not** reconcile AC, attacks, damage, save DCs, spellcasting, CR/XP or live combat state. Its arithmetic cases are not evidence of full Template, family, guided-UI or Species completion.

### M2b explicit statblock bindings (internal foundation only)

`js/creature-transformation-bindings.js` adds the pure `compileCreatureTransformationBindings({current, abilities?, chassisSource?, armor, entries, proficiencyBonus?, nextProficiencyBonus?})` API. It compiles declarations into frozen `setArmorClass {value}` and `setEntryNumbers {section,match,entries}` setters. These setters, and the innate setter below, are permitted only in opt-in v2 snapshots, never default recipe/option changes, legacy operations or M1 Dracolich. They carry concrete values/content, not executable bindings, paths, expressions or catalog references. Entry replacement changes only `entries` (or `headerEntries` for `spellcasting`); other entry metadata, uses, spell lists, slots and source identity remain intact.

AC requires either `{mode:"retain"}` or `{mode:"recalculate",alternatives:[...]}` with one declaration per existing alternative in its existing order. Each alternative is either `{mode:"retain"}` or `{kind:"worn"|"natural"|"unarmored",base,dexterity:"none"|"full"|"capped",shield,fixed,maxDex?,minimum?}`. `maxDex` is required only for capped Dexterity; a negative Dexterity modifier is not raised to zero. The declared base, Dexterity, shield and fixed contributions must exactly explain the current AC before a changed score is used. An optional new `minimum` floors only that alternative. Existing equipment links, natural-armor labels, conditional text and braces are retained; a conditional alternative is never made unconditional. Supported AC is a bounded array of numbers or `{ac,from?,condition?,braces?}` objects. Special AC requires an explicit retain policy. Armor names/prose are not used to infer equipment or Dexterity rules.

Each entry declaration identifies `{section,match:{name,source},mode}` exactly, with a concrete source (not a role or `$chassis`). `mode:"retain"` deliberately preserves the entry. `mode:"bind"` additionally requires `numbers`, declaring **every** `hit`, `dc` and `damage` tag in that entry. A number selects a zero-based top-level `paragraph`, `kind` and zero-based `token` within that kind. `mode:"ability"` supplies `ability`, `proficiency` (0, 1 or 2), and `fixed`: the value is ability modifier + multiplier * explicit PB + the non-PB fixed contribution (including the usual DC base 8). `mode:"fixed"` supplies the exact current `value` and retains it, irrespective of changed scores/PB. For damage, `value`/the computed contribution is the dice bonus; both modes also declare `dice:{number,faces}`. The current dice, bonus and adjacent printed average must agree before the compiler updates both the roll tag and its rounded-down average. Unchanged tags retain their original bytes. Other text, distances, recharge/uses, durations, damage types, poison riders and fixed donor values are untouched.

Every current entry containing these numeric tags (including spellcasting headers) or an untagged `DC N` requires an explicit declaration. Missing/duplicate/source-ambiguous bindings, unexplained contributions, missing explicit PB, custom/mixed damage expressions, mismatched custom averages, untagged DCs in computed entries, or nested numeric entry content fail with `CREATURE_TRANSFORMATION_INPUT_REQUIRED`. Explicit entry retention is available; it is not guessed from prose. This bounded API does not parse arbitrary homebrew attack prose, custom tag display arguments or unrestricted expression trees. Callers changing PB must also use the M2a numerical compiler so the actual PB and all dependent saves/skills stay coherent; the M2b-only Zombie producer below does not change PB.

**Actual catalog producer coverage:** pending staged `Zombie|DMG` can now receive `inputs:{bindings:{armor,entries,proficiencyBonus?}}` through the existing per-target workflow. Omit `bindings` to retain the accepted M2a-only behavior. With bindings, its actual DMG score adjustments feed the compiler, and its concrete receipt additionally contains `automation-bindings:["zombie-dmg-m2b"]`. Real MM Bugbear controls exercise STR 15 -> 16, Morningstar hit +4 -> +5 and `11 (2d8 + 2)` -> `12 (2d8 + 3)`, both Javelin damage alternatives, prior-history compilation and both operation consumers. Real Drow controls exercise CHA 12 -> 8 and innate DC 11 -> 9 without changing its spell uses or fixed poison DC. Zombie does not change Dexterity or grant armor/spells: at M2b, changed AC, new innate grants and changed-PB/expertise arithmetic are **foundation API/setter coverage**, not catalog producer or family-completion claims. M3 below additionally exercises changed PB through the existing producer. No additional catalog record is enabled or added.

**Complete innate foundation API:** `compileCreatureTransformationInnateSpellcasting({current,abilities?,proficiencyBonus?,nextProficiencyBonus?,spellcasting})` accepts `{name,source,ability,dcFixed,attackFixed,components,spells}`. DC = ability modifier + explicit PB + `dcFixed`; attack = ability modifier + explicit PB + `attackFixed`. It returns `addInnateSpellcasting {name,source,ability,saveDc,attackBonus,components,spells}` with concrete numbers. `components` explicitly lists required `"V"`, `"S"` and/or `"M"` (an empty array means no components). Each spell has an explicit `name|source` UID and `usage:"will"|"daily"|"rest"`; daily/rest entries also require `uses:1..9` and `each:boolean`. `each:false` preserves a shared use pool; `each:true` uses the renderer's `Ne` per-spell convention. Optional `restriction:"selfOnly"` retains that bounded source restriction. Edition-qualified UIDs are preserved, not redirected or normalized to another edition. Other restrictions/component rules are unsupported inputs, not invented defaults.

The executor appends a source-qualified innate block with actual ability, DC, rollable spell attack, uses and explicit component requirements, with no Species-style "DM determines" placeholder. Existing innate/known/prepared spellcasting is retained unchanged; this API neither creates slots nor repurposes legacy `grantSpell`. Strict validation prevents duplicate spell UIDs and missing uses/components. Real renderer, JSON replay and removal controls exercise this setter, but **no staged catalog recipe currently produces a new innate grant**. The setter fixture is explicitly labeled as such.

AC and entry/spell setters join the existing v2 dependent numeric conflict group: retain the entire group, apply the entire group, or withhold it pending decisions; mixed winners require new reconciliation. Apply also fences changed input answers even when two declarations happen to compile to identical concrete values. Existing consent, integrity, catalog/history fences, storage preflight, per-target isolation and frozen replay/removal remain in force. M1 snapshots, default/legacy output and Species are unchanged. M2b alone does not estimate CR/XP; the separately opt-in M3 foundation follows. Forms/editor, family completion and rollout remain later milestones.

### M3 estimated CR foundation (internal only)

`js/creature-transformation-cr.js` exports the pure `estimateCreatureTransformationCr({current,table,assumptions,proficiencyBonus?,proficiencyContext?})`. `current` supplies **post-transformation** HP/AC; `table` must be the 34 ordered rows loaded from this checkout's `data/msbcr.json`, not the DOM calculator, scaler or a feature-expression table. The result is a concrete `setChallengeRating {value:{cr,xp},receipt}`. The receipt explicitly labels the method `dmg-2014-v1`, estimated/defensive/offensive CR, effective HP/AC, selected routine/DPR/accuracy, all supplied assumptions, override and PB provenance. Arithmetic follows DMG 2014 pp. 274-275, 277-278 and regeneration guidance on p. 281. This is an estimate, **not** a playtested rating or a 2024-specific CR model.

The closed numeric assumptions are required, not inferred from arbitrary attack/feature prose:

| Input | Supported meaning |
| --- | --- |
| `defense:{expectedCr,hpBoundary,acIndex,acAdjustment,hpAdjustment,resistance,vulnerability,regeneration,note}` | Explicit expected CR anchors the defense multiplier; it does not iterate with the estimate. Select an existing AC alternative by zero-based index, including any adjudicated conditional equipment/spell state. `resistance` is `"none"`, `"resistance"` or `"immunity"`: the DM decides whether enough relevant damage types actually warrant the DMG multiplier; one poison immunity does not automatically double HP. Resistance bands 0–4/5–10/11–16/17+ use 2/1.5/1.25/1; immunity uses 2/2/1.5/1.25. `vulnerability:true` means the DM specifically adjudicated prevalent multiple vulnerabilities. Effective HP = floor(actual HP × defense multiplier × vulnerability factor + 3 × regeneration + hpAdjustment). `regeneration` is the applicable HP regained each round, not extracted from a trait's name. Other effective HP/AC adjustments require explicit amounts and the source-policy `note`; actual HP/AC is not changed by these estimate-only adjustments. |
| `hpBoundary:null \| "lower" \| "higher"` | Within `defense`. Ordinary unambiguous lookups need no choice (`null`). The version-matched source table overlaps at **760 HP (CR28/29)** and **805 HP (CR29/30)**; those exact lookups require an explicit lower/higher policy. No source-table edit or silent first/last-match selection. |
| `routines:[{id,rounds,accuracy,note}]` | One to twelve complete alternative three-round routines, not individual attacks to blindly add together. `rounds` has exactly three `{value,proficiency}` totals, including the adjudicated attack counts, targets, recharge/uses, ongoing and off-turn effects. Values are **post-ability, pre-PB** totals. For each candidate PB, add `proficiency × (candidate PB − current PB)`; this explicitly supplied damage coefficient is 0–100, never inferred from magnitude. `accuracy:{kind:"attack" \| "save",value,proficiency:0 \| 1 \| 2}` declares the predominant attack/save measure and its exact PB contribution. Source-fixed donor damage/DC uses coefficient 0, irrespective of changed CON/PB. `note` records the routine/source adjudication. |
| `routine:"highest-damage" \| routineId` | Select the complete routine with greatest floor(three-round total / 3), or explicitly choose one. Highest-damage ties require a concrete choice; the helper does not invent an attack-vs-save interpretation or combine incompatible alternatives. |
| `review` | Nonempty confirmation that all relevant effects/routines were reviewed and represented. This is a required guided/source-policy input, **not an automatic completeness detector**. The caller must resolve unmodeled features before estimating; review text is never evaluated. Numeric totals are supplied adjudications, not independently extracted or verified against arbitrary entry prose. |
| `override:null \| {cr,reason}`, `zeroXp:boolean`, `proficiencyAnswer:null \| {mode,value,reason}` | A canonical CR override retains the separately computed estimate and the reason. XP is replaced canonically using Parser's XP table; old custom XP does not survive as a stale value. CR0 normally grants 10 XP; `zeroXp:true` explicitly selects its no-threat 0 XP exception and is invalid for any other final CR. An ownership answer uses `mode:"derived" \| "source-fixed"` and the exact current PB; it resolves genuine history ambiguity or explicitly fixes a formerly generated PB, never silently overwrites an authored/custom PB note. |

HP and DPR select table rows; each complete two-point AC or predominant accuracy difference moves one row, with CR0 as the floor. The numeric mean of defensive/offensive CR is rounded to the nearest canonical CR, taking the higher exact tie (including fractional ratings). Effective HP must be 1–850 and DPR 0–320; adjusted CR above 30, missing/special AC/HP, negative damage, malformed/sparse inputs, unsupported fields and unresolved choices fail with `CREATURE_TRANSFORMATION_INPUT_REQUIRED`. No high-end cap or CR0 success-shaped fallback is used. Lair/coven/conditional CR objects need a later source-specific policy rather than dropping their fields. The existing Encounter assessment's conservative prose prefill, rounding and capped arithmetic are deliberately not imported or rewritten.

**Finite PB reconciliation:** ordinary PB derives from canonical current CR only when no source-authored `profBonus`, numeric `pbNote` or supplied source PB applies. Source PB stays fixed even if the new CR's canonical PB differs; receipts record both. Ordinary estimation exhaustively checks the eight possible table PB values **2 through 9**, accepting exactly one fixed point. There is no convergence loop or last-iteration fallback: zero/multiple fixed points require resolved assumptions or an explicit CR override. A derived-PB override evaluates its one canonical PB; source-fixed PB evaluates only its retained value. Every evaluated numeric hypothesis must remain in the supported domain; an out-of-domain hypothesis fails explicitly rather than being silently discarded. Ambiguous/disagreeing/custom PB notes still block before any paired field is overwritten.

**Actual producer boundary:** only pending opt-in `Zombie|DMG` additionally accepts per-target `inputs:{bindings,proficiencies?,cr:{table,assumptions}}`. M3 requires the existing M2b armor/entry declarations; `proficiencies` uses M2a's exact `save`/`skill` multiplier maps whenever PB changes. The compiler first obtains the actual target/history's changed abilities, CON HP and bound AC, estimates against those values, then compiles the final PB through the accepted M2a/M2b policies. Declared expertise, passive residuals, armor/entry retention and source-fixed donor numbers remain intact; no `ScaleCreature.scale` call or unrelated stat scaling occurs. `profBonus` and canonical `+N` `pbNote` remain paired even for source-fixed PB. The concrete snapshot requires all three receipts `automation-numerics`, `automation-bindings`, `automation-cr:["zombie-dmg-m3"]`, one matching PB setter and one CR setter. CR/XP joins the **same atomic numerical conflict group**, never a separate winner.

The narrowly extended workflow bridges PB ownership from **validated actual replay/write evidence**, not a catalog lookup or an earlier receipt alone. It distinguishes applied from retained numerical groups, checks an actual replay prefix when operation removal may have eliminated an old conflict, honors later explicit PB patches even when the value is unchanged, and freezes the owning operation index/integrity plus any answer. Unclassified intervening operations require an explicit ownership answer rather than treating generated PB as authored or stripping source fields. Direct pure/compiler calls without this workflow context treat an existing numeric pair as authored; the workflow is the repeated-estimate integration boundary. No operation-engine rewrite or new statblock metadata is involved.

M3 controls separately prove pure numerical examples and the real Zombie producer → preview → JSON operation → Bestiary/Encounter replay/removal path. A planted production-call violation using pre-transformation HP fails the real prior-history CR/XP oracle, then passes after restoration. Table/catalog removal after save does not alter replay: saved operations contain concrete setters and strict frozen receipts, **not** executable assumptions, live table rows, profile descriptors or recomputation callbacks. Removing history never regenerates formerly unchanged entries; if the resulting chassis no longer matches declared bindings, a new preview requires explicit corrected/retained source policies rather than guessing residuals. Raw-answer/table/history/catalog fences, consent, integrity, atomic saves, storage/op ceilings, legacy/M1/M2 compatibility and Species behavior remain unchanged. No default resolution, editor, new catalog family, guided DOM, rollout or full browser verification is included.

### M4a frozen form operation kernel (internal only)

`js/creature-transformation-forms.js` adds a finite frozen envelope, not a catalog producer or polymorph interpreter. **No existing family authors forms, and the editor/default resolver does not opt in.** Kernel fixtures explicitly use synthetic profiles; they are not source-defined Zombie, Vampire or Lycanthrope forms. Guided inputs, form controls and default rollout are separate milestones.

`createFrozenCreatureTransformation({profiles,activeForm,baseline})` requires 2–8 independently compiled concrete v2 leaves against the same effective pre-owner history. Each profile is `{id,label,resolved}`; IDs are unique lowercase slugs of at most 40 characters, labels at most 80 characters, and each leaf has at most 256 changes. All leaves share their source-qualified root/identity, provenance, eligibility, prerequisites and selected root options. The result is the active leaf plus `frozenForms:{version:1,baseline:{sourceUid,key},activeForm,profiles}`. The outer projection must exactly match its selected permitted leaf. Leaves cannot contain another envelope or pending automation. Species and arbitrary operation/path/expression programs are not permitted. The schema's `compiledFormLeaf`, `frozenForms` and `frozenFormResolved` definitions describe pre-adapter (`op`) output; the adapter normalizes every leaf and active projection together, and runtime checks the strict saved (`type`) payload and cross-field invariants.

Obtain `baseline` from `BestiaryQuickActionsUtil.getCreatureTransformationBaseline({baseCreature,operations})` at the intended owner position. It hashes the original source UID and **raw** pre-owner replay state using the existing canonical digest, before deferred effects and PB text finalization. This is a freshness/integrity token, not a cryptographic security guarantee. New envelopes block if that baseline changes; they never recompile automatically. Legacy/unversioned/M1/M2/M3 snapshots without this envelope retain their existing replay/removal behavior.

Create the initial operation through the normal preview/consent/conflict/operation APIs. All permitted profiles and the active choice are covered by the existing full-operation integrity. Replay and switching use only those saved concrete leaves, with no live catalog/table lookup or compilation. Existing numeric fields still share their whole-group conflict winner; a form is not an extra ability/AC/rider application.

`previewCreatureTransformationForm({target,operationId,formId,conflictDecisions?,validateChange?})` previews a saved owner's permitted leaf against its original prefix and replays the **entire unchanged suffix**. It returns a whole-history before/after diff, or unresolved owner conflicts. Downstream eligibility, entry matches and saved conflict values/keys must remain valid; a failure blocks without rewriting any later receipt. A same-active selection returns `noChange:true`, an empty diff and no applicable change. `validateChange` may preflight the resulting operations against the consumer's storage limits. `createCreatureTransformationFormChanges({batch,target,operationId?,formId?,conflictDecisions?})` rechecks the full preview/target/history/form/decision snapshot and returns either no changes or one replacement:

```js
{id: targetId, addOperations: [], removeIds: [], replaceOperation: {
  operationId: ownerId, expectedIntegrity: oldIntegrity, operation: replacementWithSameId,
}}
```

Replacement is exclusive with additions/removals. The Quick Actions utility, Registry and Encounter adapter/state retain the owner ID/index, immutable permitted set/root/baseline and consent, then validate full replay before publishing/saving. The replacement helper requires the authoritative `baseCreature` and compares actual downstream transformation conflict keys, winners and prior-writer/value context before and after the switch, including conflicts that disappear when an optional setter is withdrawn. Such a change blocks even if ordinary replay would filter away that saved decision; conflict-free optional withdrawals remain allowed. This additional fence applies only to form replacement, not ordinary legacy replay or history removal. Unrelated later operations retain their exact order and bytes. Repeated A/B/A does not stack; removing the owner removes the entire bundle subject to genuine downstream validation. Saved CR assumptions/overrides are read-only during selection.

The entire bundle remains inside the normal 180,000-byte transformation limit. Encounter additionally retains its 200,000-character wrapper and 100-operation limits: replacing slot 100 stays at 100; append 101 fails. Registry has no new global count cap. Persistent writes still commit once before assigning state/notifying; failed saves leave the old owner, HP/temp HP and groups unchanged. Changed effective HP and grouping retain their ordinary Encounter consequences, and a saved refresh failure remains labeled as saved.

### M4b typed target answers and routine composition (internal only)

`js/bestiary/bestiary-transformation-inputs.js` is DOM-free and covers **only the already staged Zombie numerics and narrow Dracolich confirmations**. It is not a form framework, new family producer or default opt-in. M4a forms/replacement remain unchanged. The shared editor, default discovery/resolution, Species, source-family completion and rollout are untouched; guided DOM controls are M4c.

`inspectCreatureTransformationInputs({target,resolved})` reads the actual effective target/history and returns facts, separate **unaccepted** suggestions, source-qualified controls and structured `{targetId,control,selector,reason}` requirements. Facts include scores, validated HP/Hit Dice/non-CON residual, ordered AC alternatives and equipment links, agreeing explicit PB, save/skill totals and exact entry/paragraph/kind/token/dice/numeric values. The observation exports in the existing stats/bindings modules reuse their bounded parsing/validation; unsupported printed averages are not prefills. No attack, expertise, armor or proficiency meaning is inferred from matching arithmetic. Spellcasting ability and current CR are suggestions only.

Answers are `{targetKey,controls:{[controlId]:answer}}`; IDs include target ID, original source UID and exact source-qualified selector. `targetKey` includes the full baseline/history: a changed target, source or entry leaves the old draft stale, never retargeted by index/name. Numeric token answers explicitly choose `{mode:"ability",ability,proficiency,fixed,reason}` or `{mode:"fixed",value,reason}`; reliable dice/address facts are supplied by observation. Whole-entry retention requires `{mode:"retain",reason}` and cannot coexist with token answers. Armor requires explicit reviewed retention: Zombie does not change DEX/equipment or consume a new armor policy. Its HP remains the existing source-defined Constitution policy; there is no pretend retain/override widget. Save/skill answers use `{multiplier,reason}` and optional current source PB uses `{value,reason}`. Dracolich uses `{value}` confirmations for the five existing producer fields, without age/name inference or new physiology/lair mechanics.

`proposeCreatureTransformationResidual({target,resolved,tokenId,ability,proficiency,proficiencyBonus?,proficiencyContext?,proficiencyAnswer?})` computes observed token bonus minus the deliberately selected ability modifier minus the selected multiplier times current PB. It returns an immutable, target/source/token/history-qualified proposal with `fixed`, arithmetic facts, PB provenance and `accepted:false`; it never chooses ability/proficiency or fills an answer. UI callers use workflow's `proposeCreatureTransformationTargetResidual` wrapper to obtain the existing authoritative PB-history context rather than rebuilding ownership inference. Multiplier zero needs no PB/ordinary CR. Deliberate adoption uses `{mode:"ability",ability,proficiency,proposal,adopted:true,reason}` instead of hand-calculating `fixed`; compilation recomputes and compares the entire proposal against current target/token/selection/PB ownership. Missing adoption/reason, changed history and another target/token's numerically identical proposal block. Negative/nonzero residuals and separate source-fixed zero values remain valid.

`compileCreatureTransformationInputs({target,resolved,answers,table?,proficiencyContext?})` returns `ready`, `needs-answers`, `blocked`, `ineligible` or `unsupported`, with structured requirements rather than parsing compiler error strings into controls. Unexpected failures still throw. It obtains a post-ability/pre-CR-PB `projection` through the **existing compiler, adapter and read-only executor**, not a second setter interpreter. `projectionOnly:true` identifies inspection: its temporary incoming winners/provisional consent are neither returned as decisions nor saved operations. Workflow supplies the existing validated PB-history context; temporary PB for projection does not become an authored source PB.

The optional `cr` control supplies the accepted defense fields, `routines`, deliberate `routine` policy, `review:{confirmed:true,reason}`, `coverage:[{entryId,decision:"represented"|"excluded",reason}]`, override, zero-XP and PB-ownership answers. Completeness and inclusion/exclusion of every observed entry are **never prefilled/confirmed**. Each alternative has `{id,rows,accuracy:tokenId,mixedReason,note}`. Its 1–24 rows reference either an exact supported damage `tokenId` or `fixed:{value,source:{name,source},reason}`, plus exactly three `counts:0..20`, three `targets:1..100`, `timing` and `reason`. Timing is explicitly normal, conditional, off-turn, ongoing, recharge or limited-use. Fixed adjudications contribute coefficient zero. Accuracy deliberately references a supported hit/DC token, with a predominant/mixed-measure explanation.

The app computes each rounded printed per-use value, round totals and reviewed PB coefficients from selected uses/targets; separate alternatives are not summed together. Per-token rounding is preserved, including multi-target half-die means. A zero-floor crossing incompatible with M3's linear PB coefficient requires a fixed adjudication instead. Surprise Attack remains separately reviewed/scheduled, Brute's included dice are not added again and Javelin modes are not presumed cumulative. No arbitrary multiattack, spell, aura, rider or recharge prose is inferred. Unsupported token contributions remain unresolved, not zero. Source/schedule/review explanations are frozen within M3's existing note bounds.

Output is exactly the existing producer `automationInputs` (`bindings`, and optionally `proficiencies` plus `cr:{table,assumptions}`), never a saved routine program. The unchanged estimator enforces its 1–12 alternatives, explicit selected/highest-DPR policy and tie choice, table/domain/coefficient limits, exact 760/805 overlap policy, finite ordinary PB 2–9/source-fixed semantics, canonical XP/CR0 policy and independent estimate/override reason. Defense uses actual post-transform HP and the deliberately selected AC alternative/expected-CR anchor; zero resistance/regeneration/feature adjustments still require explicit review. `estimate.label` reads **DMG 2014 estimate, not playtested**. `pLoadCreatureTransformationInputTable({requested,dataUtil?})` loads `data/msbcr.json` only when explicitly requested; failures remain hard. No table/scaler/DOM-calculator changes are involved.

Opt-in `previewCreatureTransformationTargets` accepts `guidedAnswers` keyed by target ID, optional `crTable` and a supplied `generation` identity instead of independently supplied `automationInputs`. Unsupported staged/default identities cannot fall through as guided legacy success; ready siblings remain isolated from unresolved targets. The returned guided batch deeply freezes raw answers **and** compiled inputs/preview state. `createCreatureTransformationChanges` rechecks fresh raw answers (including explanations and changed schedules with identical totals), candidate, table, generation, full targets/histories, compiled leaves and actual conflict winners. M4c must supply refreshed identities and own consent/render clearing; B does not implement UI lifecycle management. Ordinary consent, prerequisite, numerical-group conflict, storage and stale-preview fences still apply. Saved operations contain only concrete leaves/frozen receipts and replay/remove through Registry and Encounter adapter/storage without live answers/catalog/table access.
