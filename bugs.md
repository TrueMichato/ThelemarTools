## Closed Bugs

* **Forest Sage (one spell instead of two; Arcana/Nature don't use Wisdom):** Forest Sage (Humblewood Tales partnered content, not in committed data) is a half-feat that (a) grants a choice of **two** druid/wizard spells and (b) lets you use **your choice of Intelligence or Wisdom** for Animal Handling, Arcana, Nature, and Survival checks. Two independent root causes. **(a) Spell count:** `SpellGrantParser._addSpellRef` ignored the `count` on a choose-block, always emitting a single `requiresChoice` pending entry — the Features-tab "Prepping for next level" flow (pending-pipeline only) therefore prompted once. Fixed generically: `_addSpellRef` now emits `count` (default 1, clamp ≥1) pending choices per string choose-block, benefiting every flow that uses the pending pipeline. A latent **double-grant** also existed because the progression flows (Level-Up / Quick-Build / Builder) run an inline spell picker (`buildFeatChoicesSpec` + `applyFeatBonuses`, which already honors count) **and** call `addFeat → _processFeatureSpells` (pending pipeline). Fixed with a new `addFeat` opt `skipAdditionalSpellChoices`, passed by the three progression flows **gated** on `CharacterSheetClassUtils.hasCollectedInlineSpellChoices(feat)` (true iff the feat's `choices`/`_featChoices` carry a non-empty `spells`/`cantrips` array) so respec/fallback paths that never ran the picker still get pending choices (no zero-grant). The skip is **surgical** — `_processFeatureSpells` suppresses only `requiresChoice` entries whose `choiceFilter` is a **string** (exactly what the inline picker collects); object-shaped choose blocks (e.g. Initiate of High Sorcery's `innate._.daily` `{choose:{from:[…]}}`) are NOT collected inline and keep flowing through the pending pipeline, and fixed (non-choose) `additionalSpells` are always granted. **(b) Skill base-ability override:** the Int/Wis swap was prose-only, and `_processFeatureModifiers` returns early when `!feature.description` — but the progression flows pass raw feats with `entries` and no rendered `description`, so no text-parsed effects ran there at all. Fixed generically: `addFeat` now derives a `description` from `feat.entries` (`Renderer.get().render({type:"entries", entries})`, guarded) and stores it on the feat, so `_processFeatureModifiers` (and other text parsers) run in every flow; uses-parsing stays gated to the *originally-supplied* description so deriving one never fabricates spurious "once per long rest" resources for official feats. A new pattern in `FeatureModifierParser.parseModifiers` recognizes "use [your] choice of {A} or {B} [modifier(s)] (to make|for) {skill list} checks", validates both abilities against `Parser.ABIL_ABVS`, unwraps `{@skill …}` tags, matches each skill against the canonical `Parser.SKILL_TO_ATB_ABV` whitelist (multi-word safe), and emits `abilitySwap:<skill>` named modifiers (one per offered ability, skipping no-op swaps). `getSkillMod`/`getSkillBreakdown` already take `MAX(default-ability mod, every swap newAbility mod)` for the skill (player-favorable, reused from the "Sixth Sense" precedent), so Arcana/Nature now use Wisdom when it's higher and Animal Handling/Survival use Intelligence when it's higher; the breakdown labels the ability line "WIS modifier (swapped from INT)". `_processFeatureModifiers` was made **idempotent** (skips a re-add when an enabled modifier with the same `sourceFeatureId` + signature exists) so deriving descriptions for official feats can't duplicate modifiers. Covered by `CharacterSheetForestSage.test.js` (22 tests); the shared test `setup.js` Parser mock gained the real `SKILL_TO_ATB_ABV` map.

* **Skill Bonus Breakdown — Magician shows as generic "Custom Modifier":** In the Nature/Arcana skill breakdown, the +3 from the *Magician* Primal Order feature (stored as a named modifier of type `skill:arcana` / `skill:nature`, name "Magician (Primal Order)") was lumped into a single anonymous "Custom Modifier" line — losing the source name. (The previously-closed "Primal Order — Magician (missing extra cantrip)" entry explicitly noted this breakdown gap stayed open; this closes it.) Root cause: `getSkillBreakdown` emitted one `{type:"custom", name:"Custom Modifier", value: getSkillCustomMod(skill)}` component, and `getSkillCustomMod` aggregates **all** `skill:<skill>` + `skill:all` named modifiers, discarding their individual names. Fixed generically so named feature bonuses always show their source: added `_getNamedModifierEffectiveValue(mod)` (the **same** perLevel / proficiency-bonus / flat-value math `_recalculateCustomModifiers` uses — `_recalculateCustomModifiers` was refactored to call it so the two can't drift) and `_getSkillNamedModifierComponents(normalizedSkill)`, which returns one `{name, value}` row per enabled named modifier of type `skill:<skill>` / `skill:all`. Both `getSkillBreakdown` branches (normal **and** lore-skill) now itemize one component per named modifier (named after `mod.name`, e.g. "Magician (Primal Order)") plus a residual generic "Custom Modifier" row **only** when `getSkillCustomMod(skill) − Σ(itemized) ≠ 0`, which preserves the hard invariant `getSkillBreakdown(skill).total === getSkillMod(skill)`. `abilityMod`-based skill modifiers contribute value 0 here (they already surface as the "Feature Bonus" line) so they're never double-counted. Covered by the breakdown-attribution cases in `CharacterSheetForestSage.test.js`; the existing `CharacterSheetStatBreakdowns` total-equals-`getSkillMod` invariant and `CharacterSheetDruidMulticlassMagician` remain green.
* **Spells tab — confusing/wrong spell & cantrip counts (multiclass):** The Spells-tab tracking header summed every caster class into a single known/prepared bucket and showed a lone aggregate count (for the test character Lunaria — Ranger 6 Hunter half-caster / Druid 3 Circle of the Zodiac full caster — this read a baffling "1/12": `preparedMax = ranger 6 + druid 6` and `currentPrepared` only counted spells whose `prepared` flag was true). Counts are player-chosen `current/max`; subclass/feature-granted spells (e.g. Zodiac's always-prepared Guiding Bolt, the Magician bonus cantrip) are surfaced separately as `+N granted` and excluded from the cap. Wizard spellbook classes (`mechanic === "spellbook"`) show a capless count to avoid a false over-limit. Spells whose `sourceClass` matches no card fall into an **"Other / Unattributed"** bucket (`getUnattributedSpellCounts()`) so legacy/mis-stamped data is never silently dropped. The Spells tab (`charactersheet-spells.js` `_renderSpellTrackingUI` → `_buildSpellClassCard`/`_buildSpellCountChip`/`_appendGamblerRollControl`) now renders one card per class headed by the class name (or the subclass name for subclass-derived casters — Gambler / Eldritch Knight / Arcane Trickster / Architect of Ruin), each with Ability • Save DC • Spell Attack and clickable Spells/Cantrips chips; the static single-ability header and the four fixed tracking boxes in `charactersheet.html` were replaced by a JS-rendered `#charsheet-spellcasting-stats` container (the primary card keeps the legacy `#charsheet-spell-ability/-dc/-attack` ids for back-compat, and every card carries the `.charsheet__spell-ability/-dc/-attack` classes the E2E spec accepts). Clicking a chip opens a **class-scoped** Add-Spell modal: `targetClass` is threaded `_showSpellPicker(targetClass)` → `_pShowSpellPickerModal({targetClass})` → `_addSpell({targetClass})` → `CharacterSheetClassUtils.pickAddedSpellAttribution({…, targetClass})`, which stamps the correct `sourceClass`/`sourceFeature` authoritatively (Gambler→`Gambler`, Wizard→`Wizard Spellbook`, else known/prepared) — and the global multiclass Add button now feeds the same `targetClass` path, killing the old first-class-wins heuristic. The Add-Spell modal status bar and the known/prepared/edition labels were dropped in favour of the per-class breakdown chips. The Gambler "roll for prepared" control moved onto its card, and `_togglePrepared`'s rolled-cap enforcement was re-keyed on the spell's own Gambler attribution (with a single-class back-compat fallback) so it works for multiclass Gamblers where the aggregate `getSpellcastingInfo()` drops `isRolledPrepared`. Verified end-to-end in `charactersheet.html` with Lunaria: two cards — Ranger (Wisdom, DC 15, +7, Spells 8/6) and Druid (Wisdom, DC 15, +7, Spells 4/6 +1 granted, Cantrips 2/3 +1 granted) — no orphan bucket, no known/prepared/edition labels. The legacy `getSpellcastingInfo` / `_getClassSpellcastingInfo` output shape and `getSpellSaveDc` / `getSpellAttackBonus` values were left byte-identical so all existing suites stay green. Covered by `CharacterSheetMulticlassSpellcasting.test.js` (18 tests) plus new attribution cases in `CharacterSheetCantripPreparedCounts.test.js`; full charactersheet suite (8748 tests) green.

Each per-class card displays its own ability/DC/attack; the Combat tab header (`charactersheet-combat.js` `renderCombatSpells`) and the Overview quick-spells header (`charactersheet.js` `_renderQuickSpells`) now show the shared value when all classes agree, otherwise **"Varies"** with a per-class tooltip (Gambler contributes its dice formula). Gambler stays a per-spell mode keyed on `spell.sourceClass/sourceSubclass === "Gambler"` (fixing a latent bug where a Wizard spell on a Wizard/Gambler character would roll Gambler dice). Verified with Lunaria (both classes WIS → DC 15 / +7 on both cards, with the combat/overview headers collapsing to the shared value and listing `Ranger: 15 • Druid: 15` / `Ranger: +7 • Druid: +7` in the tooltip) and unit-tested with a Wizard/Cleric pair that yields **different** DC/attack per class. * **Metamagic hover showed the sorcery-point cost twice (Sorcerer):** Hovering a Metamagic option rendered the cost on two lines — a leading "Cost: 1 Sorcery Points" (usually *wrong*) followed by the correct inline cost. Root cause was **data duplication, not a render bug**: every one of the 21 TGTT metamagic optional features (`featureType: ["MM"]`) in `homebrew/TravelersGuidetoThelemar.json` carried BOTH a `consumes: {name: "Sorcery Points", amount: 1}` block — which the optional-feature renderer (`render.js` `Renderer.optionalfeature.getCostHtml`) prints as a leading "Cost: N Sorcery Points" line with `amount` hardcoded to 1, so it was incorrect for every variable-cost metamagic (Heightened = 3, Quickened = 2, Twinned = spell level, …) — AND a hand-authored inline first entry `{@italic Cost: <n> sorcery point …}` with the correct, variable cost. The character sheet derives the dashboard cost from `CharacterSheetState.TGTT_METAMAGIC[key].cost` (correct), and the only code that reads `consumes` keys on `name === "Stamina"`, so the `consumes` block was functionally dead for metamagics and could not express "spell level"/"half your level" costs anyway. Fixed at the data root-cause (DRY, uniform): removed the redundant `consumes` block from all 21 MM optional features, leaving the single correct inline cost. Non-metamagic `consumes` blocks (5 Bardic Inspiration consumers, combat-method Stamina, etc.) were deliberately left intact. Covered by `CharacterSheetMetamagicCost.test.js` (5 tests asserting no MM `consumes`, inline cost present on every MM feature, and non-MM `consumes` preserved).

* **Divine Soul affinity spell was locked (should be swappable for another Cleric spell) (Sorcerer):** A Divine Soul Sorcerer gains one always-prepared spell determined by their alignment affinity (Good → cure wounds, Evil → inflict wounds, Law → bless, Chaos → bane, Neutrality → protection from evil and good). The rules let the player change *that one* spell for another Cleric spell, but the sheet rendered it like every other subclass-granted spell — with a disabled "Locked" button. Fixed with a real, restricted swap picker plus a generic "effective grant" seam (architecture-first, single source of truth): added `CharacterSheetClassUtils.getEffectiveDivineSoulSpell(subclass, subclassChoice, override)` (returns the per-class `divineSoulSpellOverride` if set, else the alignment-derived default), and routed `getDivineSoulKnownSpell`, `ensureDivineSoulKnownSpell`, and `getSubclassAlwaysPreparedSpells` through it so no call site re-derives the grant. The affinity entry is now tagged `isDivineSoulAffinity` in `_buildSubclassSpellEntry` (and `addSpell` was fixed to persist the flag, which it previously dropped when rebuilding the entry); `populateSubclassSpells` stamps the tag onto pre-existing/legacy entries so old saves gain the Swap affordance on load with no explicit migration. New `state.swapDivineSoulAffinitySpell(className, newSpell)` records the override and does a **targeted** removal of only the current affinity grant via `_removeDivineSoulAffinityEntry` (matches the `isDivineSoulAffinity` tag by name — enrichment can rewrite a PHB ref to XPHB — or an exact `name|source` under the `"<sub> Spells"`/`"<sub> Affinity"` feature for that class; never a broad `removeSubclassSpells`, which could nuke a colliding player-owned spell), then repopulates. The override is cleared (and the stale spell removed) when the affinity changes (`setSubclassChoice`), when switching to a non-Divine-Soul subclass (`setSubclass`), and on subclass removal during level-down (`removeClassLevel`). The Spells tab (`charactersheet-spells.js _renderSpellItem`) now shows an enabled **Swap** button plus a reminder line for affinity entries; the delegated handler opens `_pSwapDivineSoulAffinity`, which restricts candidates to the subclass's granted/expanded list (`getAdditionalSpellListClasses` → `["Cleric"]`) at the affinity spell's level (1) via `spellIsForClass`, then applies the swap, re-renders, and saves. Covered by `CharacterSheetDivineSoulSwap.test.js` (11 tests: population/tagging, default + override resolution, targeted removal, source-rewrite robustness, collision safety, affinity-change cleanup, subclass-switch cleanup, and toJson/load persistence).

* **Zodiac Star Map (generic 3-use resource instead of Wis-mod Guiding Bolt casts):** In the TGTT *Circle of the Zodiac* (and the official *Circle of the Stars*) subclass, Star Map surfaced as a generic resource with a flat 3 short-rest uses, with no link to the *Guiding Bolt* casting flow. Per RAW the feature grants **`max(1, Wisdom modifier)`** slot-free casts of Guiding Bolt that recharge on a **Long Rest** (the 2014/TCE version instead uses **proficiency bonus**). Three distinct defects: (1) `FeatureUsesParser.parseUses` picked the *first* rest phrase in the text, and Star Map's replacement-ceremony sentence ("performed during a Short Rest or Long Rest") precedes the actual use-recovery clause, so recharge was mis-read as `"short"`; (2) `getFeatureCalculations().guidingBoltFreeUses` was hard-coded to proficiency bonus for *both* editions; (3) there was no way to spend the resource from the cast UI. Fixed generically (architecture-first, DRY): (a) `parseUses` now prefers the canonical *"regain (all) expended uses … on a (short/long) rest"* recovery clause for recharge — benefiting every feature using standard 5e recovery wording — falling back to the old heuristic; (b) `guidingBoltFreeUses` is now `Math.max(1, wisMod)` for XPHB/TGTT and edition-aware (`profBonus`) for TCE; (c) `getFeatureCalculations()` emits a structured, data-driven `noSlotCasts` descriptor `[{spell, sources, resourceName, castLevel}]`, consumed by a new generic `getNoSlotCastResourcesForSpell(spell)` state helper; (d) `_castSpell` (charactersheet-spells.js) now unifies *no-slot resource* options with pact/leveled slot options into a single `castOptions` picker, so casting Guiding Bolt offers "Star Map — cast at level 1, no slot (n/m)". The resource is decremented **after** the metamagic/constraint/variant-component steps (refunded if the cast is cancelled), and — critically — a variant component's `noSlot` effect waives the spell *slot* but never the chosen Star Map charge (no free cast). `recalculateResourceMaximums()` keeps Star Map's max in sync with Wisdom (now also re-run + re-rendered after an ability-score edit), but intentionally does **not** sync recharge (re-parsing base text would regress features overridden elsewhere, e.g. Bardic Inspiration's Font-of-Inspiration short-rest flip — guarded by a regression test). **Migration:** `_migrateStarMap()` (run from `loadFromJson`) narrowly fixes existing saves — converts a legacy `recharge "short" → "long"` and clamps `max` to `max(1, wisMod)` using `current = min(current, newMax)` (never resets current up to max), updating both the `_data.resources` entry and the linked `feature.uses` so all panels agree; idempotent and guarded to only act when a Zodiac/Stars Star Map feature is present. Covered by `CharacterSheetZodiacStarMap.test.js` (15 tests) and `CharacterSheetZodiacStarMapCast.test.js` (4 `_castSpell` integration tests).

Five forms apply *passive* derived-stat effects that flow through the existing consumers — **Bulette** (AC + burrow), **Aurochs** (advantage + proficiency on STR checks/saves), **Horse** (walk ×2), **Octopus** (swim = walk), **Cat** (roll-floor 8 on Perception/Stealth/Acrobatics via a new active-state `rollFloor` merge into the skill-roll resolution path that auto-clears on deactivation). The seven triggered/situational forms (Beaver, Peacock, Roc, Bee, Hound, Griffon, Phoenix) render `{type:"info", label}` effect lines surfacing their **exact computed values** (reduction, save DC, damage, heal, range) from `getFeatureCalculations()`, so every form visibly "does something". The framework is tier-generic so Star Week (L10) / Full Zodiac (L14) forms wire in by adding `ZODIAC_FORM_DEFS` entries. Covered by `CharacterSheetZodiacForm.test.js` (20 tests, incl. snapshot-compounding regression for Horse→Horse / Horse→Bulette). Note: **no migration** — a character whose Druid was recorded as XPHB (no TGTT Zodiac features) must re-level the multiclass leg to receive the Zodiac subclass features (see the related Druid-multiclass closed bug).

* **Resilient (no save proficiency granted):** Taking Resilient raised the chosen ability by 1 but never granted proficiency in that ability's saving throw. Root cause: Resilient is a half-feat whose data carries `savingThrowProficiencies: [{choose: {from: […]}}]` alongside its `ability` choose-block — the save is *implicitly tied to the chosen ability* (one pick) — but **no** character-sheet code read `feat.savingThrowProficiencies`: the central `applyFeatBonuses` handled ability/skill/language/expertise/spells only, and the Features-tab inline apply (which doesn't route through `applyFeatBonuses`) likewise skipped it. A stale registry entry `register("Resilient", [{type: "saveProficiency", save: "chosen"}])` existed but its handler deliberately no-ops `"chosen"`, so nothing was applied. Fixed generically (architecture-first, DRY — benefits every save-granting feat): added `CharacterSheetClassUtils.resolveFeatSaveProficiencies(feat, choices)`, which resolves a `choose` block to the chosen ability (respecting any `from` allowlist) and also handles pre-resolved `"con"` / `{con: true}` forms, de-duped and validated against `Parser.ABIL_ABVS`. Wired it into `applyFeatBonuses` (covers **Level-Up / Quick-Build / Builder / Respec**) and the Features-tab inline apply, each calling `state.addSaveProficiency()` (which dedupes). No new picker — the save is derived from the existing ability choice, so the combined half-feat now grants both the +1 and the matching save in every flow. The harmless registry no-op was left as-is. Covered by `CharacterSheetResilientSaveProficiency.test.js` (14 tests).

* **Plantmender / uncategorized feats (missing +1 ASI):** Plantmender (Humblewood partnered content, not in the committed data) declares neither a `category` nor an `ability` grant, so no ASI picker appeared and nothing was applied — the feat-sheet picker and applier both keyed strictly on `feat.ability`. Fixed generically in code (no data edits, per design): added three pure helpers to `CharacterSheetClassUtils` — `featHasAbilityGrant()` (does the feat already grant a fixed/choose ASI?), `featDefaultsToGeneralAsi()` (uncategorized **and** ASI-less **and** not a superseded reprint → treat as General), and `getEffectiveFeatAbility()` (synthesizes a `[{choose:{from:Parser.ABIL_ABVS, amount:1, count:1}}]` grant for such feats, otherwise passes `feat.ability` through unchanged). Re-using the exact half-feat spec shape means every downstream picker/applier/validator handles synthesized grants with **zero** special-casing. Wired `getEffectiveFeatAbility()` into all spec-builders and the central applier: `buildFeatChoicesSpec` + `applyFeatBonuses` (ClassUtils — covers Level-Up, **Builder** via the shared `_renderOptFeatureFeatProgressionPicker`, Respec preview, and Quick-Build/Builder apply), Quick-Build's local `getFeatChoices`, and the Features tab's `_getFeatChoices` (its inline apply already defaulted the amount to 1). Guarded by `!feat.reprintedAs` (**Option B**) so superseded legacy 2014 feats (Alert/Lucky/Tough, which are category-less and ASI-less but carry a `reprintedAs` pointer) are **not** retroactively buffed; the predicate also never double-grants on feats that already have an ASI (Forest Sage is unaffected). Now taking Plantmender in Level-Up / Quick-Build / Builder / Features surfaces a "+1 to one ability of your choice" picker and applies it (capped at 20). Covered by `CharacterSheetUncategorizedFeatAsi.test.js` (23 tests); two pre-existing `isFeatChoiceSpecComplete` gate tests were updated to use categorized (Origin) feats so they keep isolating the skill/no-choice gates rather than the new General-ASI behavior.

* **Druid multiclassing (Specialties never offered):** Multiclassing into Druid silently recorded an empty choice set and never surfaced the *Specialties* picker. Root cause: Specialties live **only** on the TGTT Druid class (source `TGTT`); the XPHB Druid has no such feature. The multiclass class picker (`showMulticlass`) built its list from the raw, un-deduped, un-source-filtered `getClasses()`, so two "Druid" rows (XPHB + TGTT) appeared, distinguished only by tiny muted source text — and the feature-less XPHB Druid was the one that got chosen. Fixed generically (architecture-first, benefits every duplicated-name class): added `CharacterSheetClassUtils.dedupeClassesBySourcePreference()`, which collapses same-named class variants to a single preferred entry (preference order: a source the character already uses → TGTT when TGTT is enabled → XPHB → PHB → other, with a stable name-order and `localeCompare` tie-break). `showMulticlass` now runs the catalog through `filterByAllowedSources` then this deduper, so a single "Druid" row resolves to the variant whose features actually exist; the existing `_renderFeatureOptionsSelection` path then renders Specialties (and Primal Order) correctly. Note: **no migration** — a character whose Druid was already recorded as XPHB (e.g. Lunaria) must re-level the multiclass leg to pick up the TGTT Druid and its Specialties.

* **Primal Order — Magician (missing extra cantrip):** Choosing *Magician* correctly applied the Nature/Arcana bonus but never offered the extra Druid cantrip it grants. Root cause: `magicianCantripsBonus` was computed in state but never consumed anywhere. Fixed at the architecture-first integration point — the **central spellcasting cantrip budget**: `_getClassSpellcastingInfo()` now adds `+1` to a Druid's `cantripsKnown` when `hasFeature("Magician")` (both the data-driven and fallback progression branches), and `getMagicianBonusCantripCount()` was added to ClassUtils. Because the spells tab gates cantrip selection by `getSpellcastingInfo().cantripsKnown`, the extra pick now surfaces across **every** flow — builder, multiclass, respec, and already-loaded characters — the moment Magician is selected. The builder's build-time spell-picker (`_getKnownCasterInfoForBuilder`) was additionally wired to include the bonus for creation-time consistency. Covered by `CharacterSheetDruidMulticlassMagician.test.js` (16 tests). Note: the related "Skill Bonus Breakdown shows *Magician* as a generic Custom Modifier" item stays open under UI/General.

* **Hunter's Prey (consumable "Use" instead of a toggle):** The Ranger Hunter's *Hunter's Prey* surfaced as a consumable resource (max 1, short rest) because the generic uses-parser matched the "Short Rest or Long Rest … once per turn" wording and auto-created a resource. Fixed: Hunter's Prey is now a **toggle** between *Colossus Slayer* / *Horde Breaker* (plus *Giant Killer* in the 2014 ruleset), modeled on Primal Focus. Added `huntersPrey` state with `hasHuntersPrey()` / edition-aware `getHuntersPreyOptions()` / `get`/`setHuntersPreyOption()`; `getFeatureCalculations` is now option-aware (`colossusSlayerDamage` only when Colossus Slayer is active, else `hasHordeBreaker` / `hasGiantKiller`). `addFeature` no longer auto-creates a resource/uses for Hunter's Prey (treated as a resource-system/meta feature), and a `loadFromJson` migration (`_migrateHuntersPrey`) strips the legacy orphan resource + feature `uses` so existing characters (e.g. Lunaria) are cleaned automatically. The Features tab shows a **read-only** active-option display ("Swap on a short or long rest"), and both the **short and long rest modals** include a passive swap selector (per the 2024 rest-swap rule). Covered by `CharacterSheetHuntersPrey.test.js` (18 tests).

* **Fighting Style (no picker for class-level `featProgression`):** TGTT/2024 classes grant Fighting Style as a *feat* via a class-level `featProgression` entry (`category: ["FS", "FS:R"]`), but no character-sheet code read `featProgression` — only `optionalfeatureProgression` (which uses `featureType`) was wired — so the Fighting Style picker never appeared. Fixed generically (architecture-first, so every class with a `featProgression` benefits): added `CharacterSheetClassUtils.getClassFeatProgressionGains()` (sums grants over the leveled range, excludes Epic Boon category `EB` which the dedicated ASI/Epic-Boon flow already handles), then wired a category-filtered feat picker — with sub-choice support (e.g. Druidic Warrior's cantrips, Superior Technique's maneuver) — into all four flows: **Level-Up**, **Quick Build**, **Builder** (XPHB Fighter's L1 Fighting Style now surfaces too), and **Respec** (full re-pick via the real feat system). Chosen feats are persisted with a `classFeatProgression` provenance tag for cleanup/respec, and recorded in level history. Note: **no migration** — existing characters (e.g. Lunaria) must re-level the granting level (Ranger L2) to receive the Fighting Style pick.

* **Primal Focus Upgrade (spurious "Activate"/Stamina button):** The feature's description hand-wrote *Singular Focus* and *Groundshatter* as plain text with "X Stamina Points", so the activatable detector mistook it for a combat method and surfaced a misleading Activate button. Root cause: those are real combat-method entities that were accidentally duplicated as prose and never granted. Fixed: added a generic, reusable `grantsCombatMethods` field on features; `Primal Focus Upgrade` (L6) now grants the real `{@combatmethod Singular Focus|TGTT}` (Predator) and `{@combatmethod Groundshatter|TGTT}` (Prey) methods. `CharacterSheetClassUtils.resolveGrantedCombatMethods()` resolves grant UIDs against the combat-method catalog (wired into state via `setCombatMethodCatalog()`), `addFeature()` adds the granted methods, the combat panel focus-gates each method's Use button to its matching Primal Focus mode, and the parent feature is marked passive so no spurious Activate appears. Note: no migration — existing characters must re-level/re-add the feature to receive the methods.

* **Primal Focus (uses badge):** Was appearing as a Bonus Action with proficiency-bonus uses based on *total* character level (showed 4 when multiclassing). Fixed: Primal Focus no longer auto-generates a generic uses badge; instead the feature now shows two dedicated badges — **Focus Switches** (always, Ranger-level based, e.g. 2 at Ranger 6) and **Hunter's Dodge** (Prey mode only, Ranger-level proficiency bonus). Hunter's Dodge uses now scale off Ranger class level, not total level.
