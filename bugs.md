New `removeClassLastLevel(name, source)` + `getRemoveClassLastLevelPreview(name, source)` target an arbitrary class's **max-total-level** history entry (`_getClassTopLevelEntry`) and drive the confirm modal. A per-target safety guard (`_canRemoveClassLevel`, replacing the blanket `isLegacyCharacter()` gate) allows removal only when the class's recorded entries provably end at its current top class level — allow if EITHER (a) the class's recorded-entry count `=== classEntry.level`, OR (b) every total level above the class's max entry is recorded — else block "incomplete top-level history". The container's single timeline `::before` line is suppressed via a `--branched` modifier class (avoids a `:has()` dependency); per-branch lines come from `.charsheet__level-branch-entries::before`. **Migration note:** total-level re-indexing on interior removal mutates only the in-memory/saved `levelHistory[].level` ordering — **no schema change**; `feat.classFeatProgression.level` is a **class** level and is deliberately *not* re-indexed (it tracks class-level provenance, not total level — conflating the two corrupts feat provenance). **Known limitations:** the subclass-selection level used by teardown is a hardcoded helper (`_getSubclassSelectionLevel`: 3 for 2024/TGTT/most classes, 1 for Cleric/Sorcerer/Warlock/Wizard) inherited unchanged from the original `removeLastLevel` — it could disagree with data-driven level-up for a class that grants its subclass at level 2; the per-class suffix-mapping display is exact for complete or missing-prefix histories but best-effort for middle-hole histories; total-level-gated choices (e.g. a Thelemar L4 ASI+Feat) survive interior re-index applied (the character stays internally consistent); and `removeFeat` does not reverse every `applyFeatBonuses` side-effect (fixed save/skill proficiencies, immunities) — all pre-existing. Verified end-to-end in `charactersheet.html` with Lunaria (removing Druid 3 left Ranger 6 Hunter untouched; total 9→8). Covered by `CharacterSheetRemoveClassLevel.test.js` (17 tests) with no regression to the existing `CharacterSheetRemoveLevel` suite (37 tests).

* **Combat Methods (group header showed "CTM 1, CTM 2, CTM 3, CTM 4, CTM 5"):** On the Features tab, combat-method optional features were grouped under a placeholder header reading the raw degree codes instead of the tradition name. Fixed generically (architecture-first, benefits every combat-method-granting class/flow): the grouping loop now derives both the key and the human name from the tradition via the existing `CharacterSheetClassUtils.isCombatMethod` / `getMethodTraditionCode` / `getMethodTraditionName` helpers (`getMethodTraditionName` already reads the `tradition` field for the new-entity shape and falls back to the code for the legacy shape), rendering `Combat Methods: <Tradition>` and keying `CTM:<code|name|unknown>` so the two traditions never collide. ## Unverified bugs

[] Some subclasses have features that aren't fully implemented in calculations (e.g. Alchemist's Experimental Elixir count, Alchemical Savant bonus, Restorative Reagents uses). These should be added to `getFeatureCalculations()` and tested.

### Pre-existing combat-tradition findings (surfaced during round-4 QuickBuild work — triage candidates)

[] **Incremental path can still net 4 Fighter traditions.** If a base combat tradition is chosen at L1 (before the subclass exists) and the tradition-granting subclass is added at L3, the character can end up with base + subclass traditions. (The reported fresh-build co-render double-spawn IS fixed in round 4; this incremental sequence is a separate, narrower path.)

[] **No hard tradition-count validation** in either the base or the subclass combat-tradition pickers. Selection is only indirectly enforced because combat methods require chosen traditions; a hard max/min guard would be more robust.

[] **`_combatTraditions` dead lazy-init in QuickBuild.** `_resetSelections` seeds `_combatTraditions` to `[]` (truthy), so the `if (!this._selections._combatTraditions)` seed in `_renderCombatMethodsOptFeature` never runs → for EXISTING characters a QuickBuild apply can drop previously-chosen base traditions. Separate from the round-4 fixes (which don't touch this path).

[] **Subclass bonus-method application slices by `gain.newCount`** rather than the bonus-adjusted total, so subclass-granted bonus methods may be miscounted.
